为自己的 Skill 准备验证：先计划，再生成文件

对应课件第 {{PAGE:slide-09}} 页。已有 Skill 时，可先用只读自评定位缺口。自评给出问题与建议；下面的检查计划确定怎样验证。两者都不会直接生成 tests、evals 或运行任务。

1. 先确认检查什么

先准备自己的完整 Skill、输入样例和已经确认的答案或评审标准，让同一个 Chat 能读到这些材料。工单练习可借用参考包的 tests/fixtures 和 tests/expected，但自己的脚本名称、参数与输出格式以实际实现为准。使用下面的请求，应该得到一张场景表：正常、可处理变化、应停止异常，每案有输入、标准及依据、运行方式和通过条件。例如日报正常案确认平均 65，缺字段案确认停止。逐案核对计划，纠正后再确认；没有可靠依据的标准标为待确认。

若 AI 找不到文件，补充 Skill 和材料文件夹的完整路径，确认它能读取后再继续。

2. 计划确认后，再生成检查文件

留在同一个 Chat，明确回复计划已确认，再发下面的请求。它要求生成与参考包职责类似的 tests 和 evals：可机械判定的内容有程序检查，AI 任务有提示、输入和核对标准，两者共用样例与答案。写作质量等内容可保留人工或 LLM 的评审标准，不强行写成程序断言。

复制：按确认计划补齐 tests 和 evals
{{PROMPT:verification-files}}

应该看到：实际生成的文件路径、内容清单和使用说明，待确认项单列。样例放 tests/fixtures，答案放 tests/expected，程序检查和 evals 引用同一份文件，复制完整 Skill 到新目录后仍能找到。检查 Skill 名称、脚本路径、参数、输出格式和业务标准是否适用于自己的实现；my-ticket-daily-report 不能直接套用参考包中的技能名和脚本路径。生成文件后仍要实际运行，不能把“已生成”当作“已通过”。

若样例或答案还留在包外，或检查程序没有读取它声称共用的答案文件，先让 AI 修正，再运行。生成请求并不保证一次写对。

3. 运行检查，保留结果，再核对 Agent 任务

先让 AI 按新生成的使用说明运行程序检查。应该看到每案的预期与实际、命令、退出码和汇总，记录保存在包外的新目录。失败时先定位：可能是业务代码，也可能是检查程序或路径问题。不能为了显示 PASS 改掉已确认的答案。

每轮选择未使用过的输出位置，保留旧结果。若检查程序要求目录尚不存在，让程序创建，不要先手动建好。

复制：运行生成的程序检查
{{PROMPT:verification-run}}

程序检查通过后，按自己 evals.json 的一案，在新 Chat 中给 Agent 任务与输入，再保留输出和工具执行记录，交给核对者评审，操作见LLM 核对例子。使用自己的场景 ID 和实际输出文件；自己的 Skill 若输出 Markdown，就核对 Markdown，不要求它生成参考包的三个文件。程序测试通过不会替你完成这些 Agent 任务。

evals.json 怎么用：交给 LLM 核对实测结果

evals.json 保存任务与判定标准，本身不会运行或评分。Skill 作者或核对者读取它，先让受测 Agent 完成任务，再由人工或负责评审的 LLM 核对实际结果。业务同事可在安装、修改或分享前重复这组检查。

字段怎样使用
prompt / files给受测 Agent 的任务与输入；files 路径相对 Skill 根目录
expected_output / expected_file核对者使用的成功描述与已确认答案；expected_file 是本参考包的附加核对字段
assertions逐项检查的标准，需要实际文件和执行记录支持结论

例子：参考 Skill 的正常案 id=1

  1. 先按参考包 GUIDE.txt 安装现成 Skill ticket-daily-report，再把 tests/fixtures/normal.json 复制到新的验证文件夹。在 Qoder 新 Chat 中选择这个文件夹和 Skill，发送场景 1 的 prompt：
    用 normal.json 生成 2026-10-10 的工单日报，保存到新的 ticket-normal-run 文件夹。
  2. 任务结束后，保留实际生成的 report.json、report.txt 与 evidence.json。展开执行工具，把技能加载、实际脚本路径、参数、退出状态和有关回复复制为 execution-record.txt。无法取得的部分注明缺失，不凭印象补写。
  3. 新建独立的评审文件夹。复制参考包的 evals/evals.json 和 tests/expected/2026-10-10.json，保留这两个相对路径；把本次三个输出文件放到 actual/，执行记录放在文件夹根目录。另开能读取这些材料的评审 Chat，选择该评审文件夹，发送下面的短请求。受测任务只收到任务和输入，答案留给评审方。
复制：让 LLM 核对场景 1 的实际结果
{{PROMPT:eval-review}}

应该看到：逐项结论、引用的文件或日志证据、理由和本案汇总。数字应逐字段与已确认答案比对；脚本调用必须有执行记录，不能仅凭日报正确或 evidence 自报 PASS 推断。数字和文件存在性适合程序核对；过程记录也可由人工或 LLM 审阅。

示例判断：有正确日报，但缺执行记录

以下是假设材料，用来说明证据判断：已提供正确的三个输出文件，其中平均为 65、validation 为 PASS、输入 7 条、重复剔除 1 条、跨日期剔除 1 条；没有实际执行记录。

场景 1 核对项应判依据
实际选中 Skill、调用包内脚本、退出码为零UNKNOWN缺少执行记录，文件里的自报信息不足以证明实际调用
report.json 每个已确认字段正确PASS实际文件与确认答案一致
两个辅助文件存在，validation 和数量符合标准PASS提供的文件与所列字段支持这一项

本案整体为 UNKNOWN。有任何一项明确不符则为 FAIL，例如实际平均为 39；全部核对项有证据通过才能判 PASS。LLM 的结论仍要查看证据，不能凭它写了 PASS 就接受。

当前没有自动评估程序。本例由人启动任务、整理材料、发起 LLM 核对；tests/check-regression.py 只运行固定脚本。程序也能把 evals.json 当配置，用于批量发起 Agent 任务、收集记录、调用程序或 LLM 评分并汇总，但本包没有实现这条链路。一次核对不构成前面的版本比较或生产评估，比较方法见Golden Tasks 理论。

修改后，批量重跑已知案例

这就是回归检查：修过一个问题后，确认以前能处理的任务仍然正常。既要重跑程序测试，也要重跑受影响的 AI 任务评估。业务同事可以重复第四步；技术同事可以把这些检查自动化。

技术同事：批量检查参考脚本

进入解压后的 ticket-daily-report 文件夹，运行下列命令，输出使用包外的新目录。它检查参考脚本，不会自动检查自己创建的 Skill。

python3 tests/check-regression.py --out ../ticket-regression-first
场景输入应看到什么
正常normal.json，10 月 10 日5 单；完成 3、待处理 2；平均 65 分钟
变化changed.json，10 月 11 日1 单完成；平均 30 分钟
应停止missing-field.json说明缺字段；非零退出；没有成功目录
应停止conflicting-id.json说明同一 ID 内容冲突；非零退出；没有成功目录

打开输出中的 regression.json，查看每案预期、实际和差异。PASS 表示符合本案预期；FAIL 表示不符合；UNKNOWN 表示未测或无法判断。四案通过只覆盖这组脚本案例，Qoder 的发现、调用和停止行为仍需在新 Chat 中验证。

为自己的 Skill 执行验证前，先按准备验证确认场景和文件。数据任务核对数字，写作分析核对来源与内容质量，流程任务核对执行分支和停止。程序结果与 Agent 执行记录分别留存，未运行部分保持待验证。

准备分享时，换一位同事再试

带上完整 Skill、输入样例和独立预期，让同事安装同一版本，在全新 Chat 中重复正常、变化和异常案例。记录产品版本、是否找到 Skill、实际脚本、输出位置及差异。另一台机器没跑过，就保持待验证。

不同产品的技能目录

QoderWork 使用 ~/.qoderwork/skills/；Qoder CLI 用户级为 ~/.qoder/skills/，项目级为 .qoder/skills/。按当前产品指南安装，分别核对加载和运行结果。

参考包：对照已有实现

下载完整参考练习包 · 下载现成 Skill ZIP

参考 Skill 名为 ticket-daily-report，包含固定脚本和已确认的预期。它与四步中自己创建的 my-ticket-daily-report 是两个包。需要对照实现时再看；导入参考包属于练习使用现成 Skill。

安装方式见完整参考包的 GUIDE.txt，文件按深入阅读说明的参考目录组织。参考包供对照和检查使用；执行任务时，只给 AI 本案的提示词与输入。

技术同事：不经过 Qoder，直接运行参考脚本

解压完整包，进入其中的 ticket-daily-report 文件夹。需要 Python 3.9+，只用标准库。读业务规则和 tests/expected/README.txt，然后运行：

python3 scripts/pipeline.py \
  --input tests/fixtures/normal.json --date 2026-10-10 \
  --out ../ticket-first-run

生成 report.json、report.txt 和 evidence.json。核对独立预期，平均耗时应为 65 分钟。直接跑脚本不需要安装 Skill；这项检查只说明脚本本次执行情况。
