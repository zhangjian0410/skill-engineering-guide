从一次 Chat 到自己的 Skill

先把一份工单日报做对，再把这次方法保存下来，换个 Chat 继续用。

从还没安装日报 Skill 开始

准备好能读取文件、运行处理并保存结果的 Qoder。全部输入都是虚构工单，可以放心跟练。你负责确认规则、核对数字；处理代码和 Skill 文件交给 AI 整理。

  1. 普通 Chat 完成任务：得到一份核对正确的日报。
  2. 提炼 Skill：得到自己创建的完整 Skill ZIP。
  3. 安装：在已安装列表中找到它。
  4. 新 Chat 验证：只给数据、日期和输出位置，重做日报。

今天先完成这四步。批量检查、换电脑和成熟度等内容在进阶阅读，用到时再看。

1. 用普通 Chat 完成一次工单日报

现在有什么：只有一份工单数据，还没有你自己的日报 Skill。

你要做什么

  1. 下载工单样例 normal.json，保存在自己找得到的文件夹。JSON 是这次练习的数据文件，无需手工编辑。
  2. 在 Qoder 新建一个普通任务，把这份文件作为附件提供，或选择它所在的工作目录。
  3. 展开下面的提示词，复制到 Chat。此时直接描述任务，不需要选择日报 Skill。

应该看到什么

Qoder 返回日报文件的位置和计算过程。打开日报，逐项核对：

核对项本例应得到
统计日期2026-10-10
总工单数5 单
完成 / 待处理3 单 / 2 单
完成工单总耗时195 分钟
完成单平均耗时195 ÷ 3 = 65 分钟

原文件有 7 行：T004 完全重复，保留一条；T006 是 10 月 11 日创建的，本次排除。完成单耗时为 60、45、90 分钟，平均只除以 3 个完成单。这里统计的是 10 月 10 日创建工单的当前状态。

核对一致后再继续。如果平均值出现 39 分钟，让 Qoder 检查是否错误地除以了全部 5 单。如果没读到附件、没有实际处理或数字不符，先在这个 Chat 中解决，并保存核对后的日报和实际使用的处理代码。

2. 把刚才成功的方法提炼成 Skill

现在有什么：同一个 Chat 中已有输入、规则、处理代码和核对正确的日报。

你要做什么

留在刚才的 Chat，复制下面的创建提示词。自己的练习技能统一命名为 my-ticket-daily-report，方便和本页后面的参考包区分。本步只生成文件，安装在第三步做。

复制：把成功任务提炼成 Skill

应该看到什么

Qoder 给出 my-ticket-daily-report.zip 的文件位置，列出里面保存的内容：

  • SKILL.md：何时使用、需要什么输入、怎样处理、何时停止。
  • 业务规则文件：日期筛选、去重和平均耗时的口径。
  • 处理脚本：保存已经核对过的计算方法，供下次调用。

另行保留第一步的输入和确认结果，供第四步核对。如果它只在 Chat 中输出了一段说明，让它继续生成完整文件夹并压缩。打开 Skill 说明，检查规则是否与第一步一致；确认脚本只处理指定的本地文件。

有了完整 ZIP 才进入安装。业务同事无需自己编写代码，但要确认保存的方法就是刚才做对的方法。

3. 安装自己刚创建的 Skill

现在有什么：第二步生成的 my-ticket-daily-report.zip，尚未安装。

你要做什么

  1. 在 Qoder 左侧打开扩展 → 技能。
  2. 选择添加技能 → 上传技能，上传第二步的完整 ZIP。这里上传自己创建的包。
  3. 在已安装列表中确认 my-ticket-daily-report。同名技能已经存在时，先核对版本，避免覆盖别人的内容。

操作依据：Qoder 官方安装指南。不同版本的按钮名称可能略有差异，找到上传本地技能的入口即可。

应该看到什么

已安装列表里出现你的技能名称。再新建一个任务，在输入框键入 /，建议列表中也能找到它。

如果找不到，先检查 ZIP 中是否包含 SKILL.md 和所需脚本。可以把报错给刚才创建文件的 Chat，请它检查包结构。安装成功后进入第四步。

应该看到什么

Qoder 读取已安装的 Skill，调用其中保存的处理脚本，交付新的日报和核对记录。日报仍为 5 单、完成 3 单、待处理 2 单，完成单平均耗时 65 分钟。

检查执行记录中的脚本路径和输出文件，确认它确实用了你保存的方法。只看到正确数字，还需要核对实际执行过程。如果它要求你重新讲整套业务规则，返回第二步补齐 Skill，再更新安装并重试。

再试一次变化和一次异常

  • 下载变化样例 changed.json。另开新 Chat，选择同一个 Skill，把日期改为 2026-10-11，输出到另一新目录。应该得到 1 单完成、0 单待处理、总耗时 30 分钟、平均 30 分钟。
  • 下载缺字段样例 missing-field.json。另开新 Chat，选择同一个 Skill，日期仍用 2026-10-10。应该指出缺失字段并停止，不生成成功日报。

这轮练习完成的标志：普通 Chat 中做对一次，保存成 Skill 并安装；新 Chat 能复用，同口径处理变化，遇到缺字段能停下来。记下输入、日期、实际结果、输出位置和遇到的问题。

参考包：对照已有实现

下载完整参考练习包 · 下载现成 Skill ZIP

参考 Skill 名为 ticket-daily-report，包含固定脚本和已确认的预期。它与四步中自己创建的 my-ticket-daily-report 是两个包。需要对照实现时再看；导入参考包属于练习使用现成 Skill。

参考包的 GUIDE.txt 说明现成包的安装方式；fixtures/ 放输入，expected/ 放独立预期，example-results/ 放失败与修复的教学记录。

技术同事：不经过 Qoder，直接运行参考脚本

解压完整包，进入解压根目录。需要 Python 3.9+，只用标准库。读业务规则和 expected/README.txt，然后运行：

python3 ticket-daily-report/scripts/pipeline.py \
  --input fixtures/normal.json --date 2026-10-10 \
  --out ../ticket-first-run

生成 report.json、report.txt 和 evidence.json。核对独立预期，平均耗时应为 65 分钟。直接跑脚本不需要安装 Skill；这项检查只说明脚本本次执行情况。

修改后，批量重跑已知案例

在完整参考包根目录运行下列命令，输出使用包外的新目录。它检查参考脚本，不会自动检查自己创建的 Skill。

python3 check-regression.py --out ../ticket-regression-first
场景输入应看到什么
正常normal.json，10 月 10 日5 单；完成 3、待处理 2；平均 65 分钟
变化changed.json，10 月 11 日1 单完成；平均 30 分钟
应停止missing-field.json说明缺字段；非零退出；没有成功目录
应停止conflicting-id.json说明同一 ID 内容冲突；非零退出；没有成功目录

打开输出中的 regression.json，查看每案预期、实际和差异。PASS 表示符合本案预期；FAIL 表示不符合；UNKNOWN 表示未测或无法判断。四案通过只覆盖这组脚本案例，Qoder 的发现、调用和停止行为仍需在新 Chat 中验证。

为什么还要用独立预期核对

参考包中的受控教学副本曾把平均耗时除以全部 5 单，得到 39 分钟；内部数量检查仍通过。独立预期为 195 ÷ 3 = 65 分钟，批量检查因此报告 FAIL。修正分母后，四案重跑通过。

原记录在 example-results/before-fix.json 与 after-fix.json。正式参考 Skill 没有注入错误，预期文件也没有为迎合输出而修改。

遇到错误，修复规则或实现，再用新目录重跑。保留失败记录；业务规则改变时，先确认新口径，再更新预期。

准备分享时，换一位同事再试

带上完整 Skill、输入样例和独立预期，让同事安装同一版本，在全新 Chat 中重复正常、变化和异常案例。记录产品版本、是否找到 Skill、实际脚本、输出位置及差异。另一台机器没跑过，就保持待验证。

不同产品的技能目录

QoderWork 使用 ~/.qoderwork/skills/；Qoder CLI 用户级为 ~/.qoder/skills/，项目级为 .qoder/skills/。按当前产品指南安装，分别核对加载和运行结果。

QoderWork 指南 · CLI 指南

几种检查各回答什么问题

  • 本次结果核对：这份日报有没有按确认的口径算对？
  • 修改后重跑案例：已知输入和异常是否仍能正确处理？
  • Agent Evals：新 Chat 能否找到 Skill、实际调用保存的方法，并在该停的时候停止？

一次成功只证明已检查的范围。当前参考包有固定脚本教学运行记录，同事实际使用 Qoder、换机和网络组合的表现仍需各自验证。

已有 Skill 后，可以用只读自评提示词定位缺口。自评阅读文件并给出建议，实际运行记录才说明执行过什么。

文件和目录按需要增加

SKILL.md 留使用说明；references/ 放详细规则；scripts/ 放处理代码。简单文案 Skill 可以只有入口文件。课件第 6 页的三个脚本名表示职责，参考包用 pipeline.py 合并检查、处理和校验。

更复杂时，tests/ 可以放程序用例，evals/ 可以放 Agent 的新 Chat 场景。按实际任务增加，目录数量不能代替结果验证。
