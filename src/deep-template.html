为什么要经历普通 Chat、提炼、安装和新 Chat

普通 Chat 完成当次任务，积累了规则、代码与正确结果。Skill 把这些方法外化到文件中，让新的任务也能读取。安装让 Qoder 能发现这个包；新 Chat 则帮助判断它是否还依赖旧对话里的隐含信息。

安装只是保存方法的一步，不能证明方法已执行。日报正确也可能来自临时计算，所以还要核对实际使用的 Skill 与脚本。换数据和遇到异常时再试，才能看出保存的方法能否按同一口径继续工作。

新 Chat 不会自动补齐资料访问、工具和权限。Skill 提供做法，Qoder 这样的运行工具负责理解任务、调用工具和执行。具体能力还取决于资料是否可用、工具是否支持、结果是否能验收。

补充说明：资料在系统里，AI 怎样拿到？

先检查已有工具与连接器，再根据系统实际提供的入口选择方式：

  • API（系统接口）：通过系统提供给程序的接口查询数据或执行操作。
  • CLI（命令行工具）：通过命令使用现成程序或服务，适合批量处理和脚本执行。
  • 浏览器自动化：通过网页查询、点击、填写和下载。Chrome 是浏览器；Playwright 是控制浏览器的自动化工具。
  • MCP：让 Agent 连接和使用外部工具的一种标准协议；工具背后仍可能调用 API、CLI 或浏览器。
  • Function calling（工具调用）：模型请求调用某个工具并给出参数，由运行程序执行并返回结果；通常由产品或开发者处理。

这些方式可以组合使用。例如，一个 Skill 指导 AI 使用 MCP 提供的工具，而工具内部通过 Playwright 操作网页。本课先了解用途，不要求你编写接口或配置这些工具。

有稳定、获准使用的接口、命令工具或专用连接器时，可优先评估结构化调用；必须经过网页时，浏览器自动化也可能是必要路线。需要考虑页面变化、登录失效、等待、下载和人工接管。稳定、高频的处理部分可评估是否固定成程序，再比较质量、耗时和维护负担。

不能仅凭技术名称判断哪个更便宜。逐步观察和重试可能增加模型调用与耗时，固定的浏览器脚本也可以高效运行；工具定义与返回内容过多，也可能增加上下文成本。用代表性任务实际试用，再决定路线。

具体接入、选型与成本优化，后续可能单独开设专题。参考：浏览器与工具选择、MCP 用途、Function calling 机制。

处理方法：步骤、AI 推理与固定代码

对应课件第 {{PAGE:slide-04}}、{{PAGE:slide-05}} 页。Workflow 安排任务怎样推进，Data Processing 负责数据处理；两个层次都可以使用 AI 和代码。

层次日报中做什么怎样分工
工作流确认日期和口径，检查输入，处理后核验，再交付AI 理解需求和解释异常；入口与代码固定必经检查，错误时停止
数据处理去重、日期筛选、数量与平均耗时计算AI 协助理解字段；按已确认规则运行固定代码，避免每次重新推算

例如同一 ID 的耗时出现 60 和 90，固定检查应报告冲突；AI 解释差异，等业务确认后再处理。字段名或口径改变也要先确认，参考脚本会拒绝不符合契约的输入。用了固定代码仍要核对可信答案，后面的程序回归检查用于发现代码本身的错误。

Tests 与 Evals：可以共用同一套判定标准

Tests（测试）检查行为是否符合预期，例如数字是否正确、权限是否拒绝、异常时是否停止。Evals（评估）用代表性任务观察 AI 的表现，并支持版本比较与持续改进。Task eval 经常直接使用 tests 中相同的断言来判定任务成功，两者高度重叠。

直接运行脚本得到 65，证明这次计算符合预期；把任务交给 Qoder，再核对文件和实际调用，验证的是安装后能否复用。工单案例适合完成这些基础检查。要比较 Skill 的改进效果，需要一批有代表性的任务和可比较的运行记录。

评估可以由程序执行。评估程序发起 Agent 任务、收集结果，再运行 Tests 或其他评分规则。人也可以启动任务、查看记录、核对同样的标准。执行者是谁不决定它属于测试还是评估。数字、文件和状态优先用程序核对，主观质量可用明确标准请人或模型评审。

独立预期是判定依据。本例依据业务规则和明细，提前确认平均耗时为 65 分钟。这个答案可以同时供脚本测试和任务评估使用，独立性取决于依据，放在包内、包外均可。详细例子见独立预期与错误分母。

只读自评阅读规则与实现，适合发现明显缺口；它不能代替实际运行。实际表现需要输入、输出与执行记录支持。

统一目录：tests 放程序测试，evals 放 AI 任务场景

对应课件第 {{PAGE:slide-06}} 页，下面展示实际参考包。SKILL.md 留使用说明；references/ 放详细规则；scripts/pipeline.py 合并检查、处理和校验。简单任务可以只有入口文件，模板等资源按需放 assets/。

参考包与课件使用同一套目录。tests/ 放程序检查、输入样例和已确认答案；evals/ 放让 AI 完成的任务与判定标准，直接复用 tests 中的样例和答案。

├── references/
├── scripts/pipeline.py
├── tests/
│   ├── check-regression.py
│   ├── fixtures/
│   ├── expected/
│   └── example-results/

    ├── evals.json
    └── README.txt

evals.json 保存任务与判定标准，本身不会执行。要得到评估结果，还需要有人或程序发起 Agent 任务、收集真实输出和执行记录，再按标准核对。当前参考包只有固定脚本的程序测试，没有自动启动 Qoder 并评分的评估程序。

为什么还要用独立预期核对

独立预期就是运行前确认的正确答案或评审标准。本例先依据明细和业务规则算出 195 ÷ 3 = 65，再拿这个答案核对实际输出。它可以同时用于程序测试和 AI 任务评估。

参考包中的受控教学副本曾把平均耗时除以全部 5 单，得到 39 分钟；内部数量检查仍通过。独立预期为 195 ÷ 3 = 65 分钟，批量检查因此报告 FAIL。修正分母后，四案重跑通过。

原记录在 tests/example-results/ 的 before-fix.json 与 after-fix.json。正式参考 Skill 没有注入错误，预期文件也没有为迎合输出而修改。

遇到错误，修复规则或实现，再用新目录重跑。保留失败记录；业务规则改变时，先确认新口径，再更新预期。

参考包的已确认答案统一放在 tests/expected/，供程序测试和 AI 任务评估共用。“独立”指答案来自已确认的业务规则。评估时只把任务和输入交给受测 AI，正确答案由核对者保留。

进阶理论：评估 Skill 的表现

下面用三个视角理解 Evals。这是本课的教学分类，各平台的名称和范围可能不同。它们都要先明确任务和判定标准，再保留实际运行证据。

视角关注什么怎样用
Trigger Evals
触发评估		该用这个 Skill 时是否使用，不相关任务是否误触发用真实表达检查触发与误触发，属于基础验证
Task Evals
任务评估		Agent 完成一批任务的质量、成本与稳定性复用 Tests 判定成功，比较基线与新版表现
Production Evals
生产评估		真实使用中是否持续有效，出现了哪些新问题抽样评审真实任务，跟踪失败、人工接管、耗时和成本

Golden Tasks：固定一批真实端到端需求

以一个协助开发网站的 Agent 为理论示例：从实际工作中选 10 个有代表性的完整需求，覆盖登录、支付、权限、超时、异常处理等。每个需求都包含真实输入、成功条件和判定依据。这批固定任务作为 Golden Tasks；别只挑容易通过的情况，也别只凭任务数量判断覆盖是否充分。

例如一个权限场景，最终条件是无权限用户确实无法访问目标数据。先用 Tests 固定这个条件，再让不同 Skill 版本的 Agent 完成同一需求；两个版本用相同断言判定。

下面全部是假设结果，用于理解比较方法：

版本相同 10 个需求的结果成功率
Skill V1Agent 完成 6 个，未完成 4 个60%（假设）
Skill V2Agent 完成 8 个，未完成 2 个80%（假设）

V1 是本次比较的 Baseline（基线）。固定任务和统一判定方法提供 Benchmark（比较基准），运行后汇总各版本的表现。也可以根据目标选择不安装 Skill 或上一版作为基线。

这里成功率提升 20 个百分点。还要同时比较质量、耗时、Token 和失败原因：更常成功是否增加了成本？失败是规则遗漏、工具报错，还是业务口径不清？数字相同也可能有不同的交付质量，需要合适的评分标准。

什么时候才能说改进有效

两个版本使用相同任务、输入和 Tests，保持模型、工具、权限、运行预算及环境一致，每次用独立上下文。重要场景多次重复，观察成功率和耗时波动。换 Skill 的同时又换模型，就难以把变化归因给 Skill。

60% 与 80% 是教学示例。单轮 10 个任务不能证明提升稳定；需要多次重复、控制其他变量，并检查是否只对这批样例有效。保留失败任务，改后重跑；再用未参与调优的新任务检查能否推广。

上线后再看 Production

上线以后，真实请求会出现新表达、新数据和新异常。持续抽样核对结果，记录失败、人工接管、质量、耗时与成本，把代表性问题脱敏后补入任务集。离线 Golden Tasks 的分数提供参考，真实使用效果还要靠这些生产记录判断。

本课没有测量生产指标，也没有用工单练习宣称版本收益。想做自动评估时，需要执行工具启动 Agent、收集记录、调用判定规则并汇总；只有 evals 文件夹或一份计划不会自动产生评估结果。

环境：2026-10-12，macOS，Qoder 0.4.3，通用模式。从未安装 my-ticket-daily-report 开始，通过界面创建任务、生成包、上传安装，再在全新 Chat 中运行。以下保留当时版本的记录；本页当前短提示词的复测见下一项。

检查实际结果
普通 Chat生成日报与处理代码；5 单、完成 3、待处理 2、平均 65 分钟
提炼与安装生成完整 ZIP；上传后在本地 Skill 列表显示已安装
